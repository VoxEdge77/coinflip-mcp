# HANDOFF: module-03/lesson-02-mcp · на 26.11.26

## Назначение
Учебный API «подбрасывание монетки» (Flask + gunicorn в Docker) с тестовой страницей. Броски хранятся в PostgreSQL. Урок посвящён работе агента через MCP-серверы.

- `GET /` — тестовая страница.
- `GET /flip` — записывает бросок, возвращает `result`, `flip_number`, `timestamp` (из `flipped_at`, UTC). `HEAD /flip` ничего не пишет.
- `GET /stats` — `total`, `heads`, `tails` за всё время.
- `GET /health` — 200 `status: ok`, `database: ok`; без базы 503 `status: error`, `database: unavailable`.
- Ошибки — JSON `{"error": {"code", "message"}}`; без базы `/flip` и `/stats` дают 503.

## Таблица `public.coinflips`
| Столбец | Тип и ограничения |
|---|---|
| `id` | `integer GENERATED ALWAYS AS IDENTITY`, первичный ключ |
| `result` | `text NOT NULL`, CHECK: только `heads` или `tails` |
| `flip_number` | `bigint NOT NULL UNIQUE` |
| `flipped_at` | `timestamptz NOT NULL DEFAULT now()` |

Столбцов `timestamp` и `created_at` нет. В `id` есть пропуски, это нормально.

### Выдача `flip_number`
В одной транзакции:
1. `pg_advisory_xact_lock` — броски получают номера по очереди;
2. отдельным запросом `INSERT ... SELECT COALESCE(MAX(flip_number), 0) + 1`, время — `clock_timestamp()`;
3. commit снимает блокировку.

Почему так: sequence и identity оставляют пропуски после отменённых вставок, а нужны номера без пропусков, переживающие перезапуск. Блокировка исключает гонку; `clock_timestamp()` сохраняет порядок времени (`now()` — начало транзакции, до ожидания блокировки). При конфликте `UNIQUE` (запись мимо блокировки) — до 5 попыток, затем 503. При обрыве связи повтора нет: бросок мог уже сохраниться. Удаление строки из середины оставит пропуск, удаление последней освободит её номер.

## MCP-серверы
- **docker** (`mcp-server-docker`) — управление контейнерами и образами; через него остановлен и удалён старый контейнер `coinflip-api` (образ 0.1). Контейнер с `DSN` запускается только `docker run --env-file` в терминале.
- **dbhub** (`bytebase/dbhub:2.1.0`) — поиск объектов (`search_objects`) и SQL (`execute_sql`). Через него создана таблица и проверены данные. **Теперь работает под пользователем только на чтение** (со слов владельца 26.11.26; права не проверены: запрос вернул `SOURCE_UNREACHABLE`).
- Изменения структуры базы — **только через миграции, не через MCP**. Инструмент и папка миграций в проекте пока не заведены.

## Правила безопасности
- Секреты не передавать параметрами MCP-инструментов (в том числе переменные окружения контейнера).
- Не выполнять `docker inspect` для контейнеров с `DSN`; MCP-инструменты docker, возвращающие сведения о таком контейнере, тоже могут раскрыть переменные — не использовать их для него.
- `.env` не читать и не выводить никакими средствами.
- Порт публиковать только на `127.0.0.1`.
- Строку подключения, пароль и адрес базы не писать в код, логи, ответы и файлы проекта. В лог из ошибок базы идут только тип и SQLSTATE.

- Повторы при конфликте — на поддельной базе, одноразовым скриптом (удалён). Автотестов в проекте нет.

## Не проверено
- Страница в браузере (результат от владельца не получен).
- Восстановление пула после обрыва связи; настоящий конфликт `UNIQUE` в базе.

## Ограничения
- Очередь: бросок около 0,3 с, последний из 20 одновременных — 3,9 с. Страница ждёт 5 с: при большей нагрузке покажет ошибку, хотя бросок может записаться.
- Повторный запрос клиента создаёт новый бросок.
- Авторизации и ограничения частоты запросов нет; защита — только привязка к `127.0.0.1`. Наружу в таком виде не выставлять.
- Пул держит одно свободное соединение; лишние открываются под нагрузкой и закрываются.
